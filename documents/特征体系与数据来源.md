# MEMF-GEF 研究特征体系与数据来源

> 本文档以 **MEMF**（论文 32）的"实体内多模态融合"为特征组织主线，融合论文 25（主播声誉多模态销量预测）与 LiveLens（论文 34，专家特征体系）的可借鉴信号，对照第三方数据平台 **灰豚**（`与辉同行-2026-08-25 07_45_00.xlsx`）与**本项目代码实际可爬取的数据**，构建 MEMF-GEF（5 实体 + 12 关系边 + 时序切片）研究所需的完整特征体系，并逐项标注数据来源与需补充的数据。

---

## 一、研究内容与目标

**研究内容**：MEMF-GEF——基于异构关系图神经网络的多模态实体融合直播销量预测（详见 `MEMF-GEF_Douyin_Systematic_Review.md`）。相比 MEMF，新增了两类实体（**观众群体 Audience-Group**、**时序切片 Time-Slice**），并将全连接 Multi-Entity Transformer 升级为异构关系图 Transformer (HGT)。

**五类实体节点**：

| 实体 | 符号 | 数量 | 与 MEMF 的关系 |
|------|------|:---:|----------------|
| 主播 Anchor | ν_An | 1 | MEMF 原有，保留 Multimodal Transformer |
| 商品 Commodity | ν_Co | M | MEMF 原有，保留 QuadTransformer |
| 直播间 Room | ν_Rm | 1 | MEMF 原有，保留 Multimodal Transformer |
| 观众群体 Audience-Group | ν_Au | K=100 | **新增**（补 MEMF 排除观众数据的盲区） |
| 时序切片 Time-Slice | ν_Ts | T=10~20 | **新增**（直播中动态信号的结构化建模） |

**目标变量**：每件商品 $C_i$ 的预测销量 $\hat{y}_i \in \mathbb{R}^+$（回归任务，Huber Loss）。

**数据约束的关键调整**：综述中 MEMF-GEF 宣称"仅直播中公开可获取数据"。但实践中存在两个绕不开的现实——① 精确销量/销售额（训练标签）公开数据流无法提供，需第三方平台；② 主播历史数值特征（近 30 天观看量等）与观众画像属后台数据。因此本研究的落地口径为：

- **模型输入特征**：以项目代码爬取的公开实时数据为主（弹幕/点赞/观看/音视频；~~礼物~~ 见下）；
- **静态/历史特征与标签**：以灰豚第三方平台为主；
- 每条特征都标注来源，`【补】` 表示尚需新增采集/逆向/模型。

## 三、特征体系（按实体，主参考 MEMF）

### 3.1 主播实体 Anchor（ν_An）

MEMF 原始字段：`anField / anCategory / anNick / anTags / anIcon`（文本/图像）+ `anView30 / anAvgComment / anAvgLike / anCommentCount / anFansCount / anFavoriteCount / anLikesCount / anScore`（数值）。

| 特征 | 模态 | MEMF 对齐 | 数据来源 | 说明 |
|------|:---:|-----------|:---:|------|
| 昵称 anNick | 文本 | ✓ | 【爬】`get_room_status` | 已获取 |
| 主播 ID | 数值 | — | 【爬】`get_room_status` `id_str` | 已获取 |
| 头像 anIcon | 图像 | ✓ | 【爬·未解析】`data.user.avatar` / WS `User.AvatarThumb` | 需补头像 URL 解析 + 下载 |
| 个人简介/签名 | 文本 | anField | 【补】主播主页（sec_uid） | 需新增主页爬取 |
| 领域/类目/标签 anField·anCategory·anTags | 文本 | ✓ | 【补】主播主页 / 【灰】主播详情 | 灰豚本 Excel 未含，需补 |
| 粉丝数 anFansCount | 数值 | ✓ | 【爬】`SocialMessage.follow_count`（实时）+【灰】直播数据"粉丝数"=39,177,250 | 灰豚为权威静态值，代码为实时单调值 |
| 带货口碑分 anScore | 数值 | ✓ | 【灰】直播数据"带货口碑"=5 | 论文 25 的"历史声誉评分"对应此字段 |
| 近30天观看量 anView30 | 数值 | ✓ | 【补】主播主页/历史直播记录 | MEMF 核心历史特征，需积累 |
| 场均评论/点赞 anAvgComment·anAvgLike | 数值 | ✓ | 【补】历史直播记录 | 需积累 |
| 总评论/总点赞/收藏数 | 数值 | ✓ | 【补】主播主页（`total_likes`/`total_videos` 等） | 需新增主页爬取 |

**小结**：身份类（昵称/ID/头像/粉丝数/口碑分）已具备或低成本可得；**历史影响力类（近30天观看、场均评论/点赞、获赞总数、作品数）是 MEMF 主播实体的核心，当前全缺，需新增主播主页爬取或长期积累**。

### 3.2 商品实体 Commodity（ν_Co）

### 3.4 观众群体实体 Audience-Group（ν_Au，K=100）—— 核心创新

> 论文 25 的弹幕三分类（MCFF）+ MEMF-GEF 的"双层聚合聚类"是此实体的特征来源。所有细粒度行为信号代码均可实时爬取。

**第一层：弹幕级特征**（论文 25 MCFF 三分类 × 数量/语义/情感）：

| 特征 | 模态 | 数据来源 | 说明 |
|------|:---:|:---:|------|
| 弹幕内容（K1 普通重复 / K2 主播直播 / K3 产品相关） | 文本 | 【爬】`chat` content | 分类需关键词规则 + 语义模型 |
| 弹幕数量 N（总数 + 三类计数） | 数值 | 【爬】`chat` 计数 | 已具备 |
| 弹幕语义表示 T | 文本 | 【爬】content → BERT | 需 BERT-wwm 编码 |
| 弹幕情感均值/占比 S | 数值 | 【爬】content → 情感模型 | **【补】需 SnowNLP / 微调情感 BERT** |

**第二层：行为信号**（MEMF-GEF 行为向量 + 关系边构建依据）：

| 特征 | 数据来源 | 对应关系边 |
|------|:---:|-----------|
| 发言频率 / 平均弹幕长度 / 活跃窗口数 | 【爬】`chat` + `ts` | 聚类行为向量 |

| 是否关注 / 分享 | 【爬】`follow`/`social` | 互动信号 |

| @主播 / 提及主播 | 【爬】弹幕文本 | `comments_anchor` 边 |

| 特征 | 数据来源 | 说明 |
|------|:---:|------|
| 群体大小 / 活跃度均值 / 情感均值 / ~~送礼率~~ / 购买率 | 由上面两层聚合 | 送礼率不可用（见下）；其余可计算 |

**群体画像（可选，来自灰豚）**：

| 特征 | 数据来源 | 说明 |
|------|:---:|------|
| 性别/年龄/城市/省份分布 | 【灰】"观众画像" sheet（女 81.67%、25-35 岁为主、山东/河南/陕西） | 代码不可获取；作为 Room 级观众画像辅助特征 |

### 3.8 已排除的特征：礼物（❌ 采不到，2026-09-28 定案）

**结论**：`WebcastGiftMessage` **不在 Web IM 推送通道上**，本项目采集路径无法获取任何礼物数据。所有礼物相关特征（`g_t`、送礼率、`gifts_to` 边、是否送礼/送礼价值）已从特征体系中移除。

**关键证据 —— 抖音官方网页自己的 WebSocket 也收不到礼物**：

| 通道 | 规模 | `WebcastGiftMessage` |
|---|---|---|
| 本项目直连 WS | 3 个房间（带货 / 娱乐 / 团播），其中之一持续 1 小时 | 0 |
| HTTP `/webcast/im/fetch/` 轮询 | 2737 条消息 / 17 种 method / 3 分钟 | 0 |
| **官方网页自身 WS**（同端点族 `webcast100-ws-web-lf.douyin.com`） | 292 帧 / 14 种 method / 150 秒 | **0** |

官方网页收到的 14 种 method 与本项目直连所得高度重合（Member/Chat/Like/Social/Fansclub/RoomStats/RoomUserSeq 等），说明**连接本身没有降级**，是通道不承载礼物消息。

**已排除的假设**（均实测证伪）：解析/路由 bug（`_unhandled_methods` 无任何礼物相关方法名）、登录态过滤（游客态与完整 cookie 的 method 集合逐条一致）、PC 客户端画像（awemePcClient UA + `X-AWEME-*` 头 + PC 固定 cookie）、连接上下文陈旧（用 im/fetch 预取的 cursor/internal_ext/push_server_v2 重建连接）。

**解析代码本身是正确的** —— 用合成 `GiftMessage` 的 22 项断言（字段映射、`Σ(diamond×combo)`、`repeat_end && group_id>0` 跳过连击收尾、单发不跳过、送礼人去重、落盘）全部通过（`test/test_gift_parse_unit.py`）。保留解析器，通道若恢复可直接启用。

**注意区分**：直播间页面上能看到的礼物面板、贡献榜、送礼列表走的是**另外的 HTTP 接口**，不在这条 WS 上，因此「页面上有礼物」不等于「WS 会下发礼物消息」。

**若后续必须补礼物特征**，可选路径：① MITM 代理抓抖音 PC 客户端（参考 DouyinBarrageGrab）；② 逆向 HTTP 侧的送礼榜/贡献榜接口；③ 采用第三方平台（如灰豚）的礼物数据。

### 3.9 粉丝团特征（✅ 已接入，2026-09-28）—— `gifts_to` 边的替代

礼物边（`gifts_to`）因礼物消息不下发而失效后，粉丝团是**当前唯一可用的、覆盖率极高的 ν_Au → ν_An 关系证据**。

**标识来源**：`User.FansClub`（`User` 消息**字段 24**）→ `data`（字段 1），是**嵌在每个用户对象里的快照**，任意携带 `User` 的消息（chat / enter / like / social / fansclub）都可读到，**被动读取、无额外请求**。实测覆盖率 100%（Member 3686/3686、Chat 466/466）。

| 字段 | 号 | 口径 | 用途 |
|---|:---:|---|---|
| `level` | 2 | 粉丝团等级。`level > 0` 与 `anchor_id != 0` **完全等价**（交叉表零例外） | 判「是否成员」、等级分布、平均等级 |
| `anchor_id` | 6 | 粉丝团**归属主播 ID**，覆盖率 ~100% | 「哪个粉丝团」的标识 + 关系边终点 |
| `status` | 3 | `user_fans_club_status`。**0 = 非成员**（`level=0` 时 100% 恒为 0，交叉表零例外）；**1 与 2 的语义未定标**（两房间分布不同，成因未定） | ❌ 只记录原始值，不作特征 |
| `club_name` | 1 | 粉丝团名称，覆盖率**房间相关**（娱乐团播 4~8%，带货 **0%**） | ❌ 不用作标识；团名兜底来源是 `FansclubMessage.content` 明文 |

**已接入的三类特征**（`data_recorder.py`，`room.json` / `series.jsonl` / `fansclub_edges.jsonl`）：

| # | 特征 | 落盘位置 | 实测（与辉同行 10min） |
|---|---|---|---|
| 1 | **群体级构成**：`member_ratio` / `level_mean` / `level_dist` / `anchor_member_counts` | `room.json` → `fansclub` | 占比 **0.5067**、均值 **7.21**、成员 1969 / 用户 3886 |
| 2 | **时序信号**：成员占比漂移 + 事件累计 | `series.jsonl`（随 `stats` 快照） | 158 条快照，占比 0.0 → 0.506 收敛 |
| 3 | **关系边**：`fansclub_of`（ν_Au → ν_An） | `fansclub_edges.jsonl`（仅成员，逐用户一行） | 1969 条，与 `member_count` 一致 |

**粉丝团消息计数（2026-09-29）**：

| 字段 | 内容 |
|---|---|
| `fansclub_event_count` | **全部** `FansclubMessage` 条数（**全量，不分 type**） |
| `fansclub_join_count` | **type=2（加入）** 条数 |
| `fansclub_upgrade_count` | **type=1（升级）** 条数 |

`room.json` → `fansclub` 下另暴露：`join_seq_first` / `join_seq_latest` / `club_names` /

`fansclub_upgrade_count` / `fansclub_join_seq_latest`。按 type 的原始分布始终保留在

（~0.1 条/分）。

#### 3.9.1 加入粉丝团：`content` 明文公告解析（✅ 2026-09-29 引入）

`FansclubMessage.type` 语义：**1 = 升级 / 2 = 加入**，二者均带明文 `content` 公告。
`liveMan.parseFansclubContent()` 把公告解析成结构化字段：

| 模板 | 例（真实语料） | 解析结果 |
|---|---|---|
| type=2 | `恭喜 敏敏～A 成为第1597966名爱生活成员` | `fc_join_seq`=1597966、`fc_club_name`=`爱生活` |
| type=1 | `致橡树 刚刚升级至【与辉同行】粉丝团 Lv14` | `fc_upgrade_to_level`=14 |

**⚠️ 两个模板里的名字含义不同，混用会串**：type=2 的 `爱生活` 是**粉丝团名**；
type=1 的 `与辉同行` 是**主播名**（实测同一 `anchor_id=3250600708947220`，type=2 给「爱生活」、
type=1 给「与辉同行」）。故 `fc_club_name` **只从 type=2 取** —— 它也是带货房间团名的唯一来源
（`user.fans_club.data.club_name` 在带货恒为空）。

**★ `fc_join_seq` 是全链路唯一的无偏累计计数器。** 「第 N 名…成员」的 N 由服务端给出，
**不受我们采样影响**：两条 join 事件的序号差 = 期间**真实**新增成员数（不是我们观测到的数）。
它是已舍弃的 type=6 缺失的那个性质，且**不需要任何定标**（正文自带语义）。实测与辉同行
1597966(09-28 17:38) → 1597992(09-29 09:29) → 1597993(09-29 09:47)，单调递增。
代价：type=2 极稀疏（~0.1 条/分），差分分辨率低，只适合长窗口。

**模板缺口监控**：`unparsed_by_type` 记录 type=1/2 未命中已知模板的条数 —— 出现非 0 说明
抖音改了文案，此时该场 `join_seq` 不可用，须回看 `events.jsonl` 的 `content` 原文补模板。
（**不静默**：宁可计数异常，也不要无声丢失。）

**type=6（占 ~95%）已决定不采用。** 其语义曾定标为「灯牌点亮」的静默状态同步，但：
① 获取**完整性不可测** —— 非循环翻转见证检验在现有语料上取不到样本（0 个可用翻转对）；
② 到达**高度爆发** —— 单场 0.30~12.51 条/分，40 倍方差且与房间热度无关。
定标与舍弃理由的全过程保留在 `modify.md` 2026-09-29（续）。

**未纳入的**：个体 `level` **不作为**行为预测特征 —— 实测判别力与直觉相反（成员占弹幕用户仅 14.0%，而全体基线 48.2%；成员占关注用户 1.4%），且 92.9% 的用户 10 分钟内只出现 1 次，个体特征不稳。

**⚠️ 可信度前提：`user_id` 打码。** 部分房间把全体 `user_id` 置为 `111111`（实测爱乐-L 娱乐团播 **100%** 打码、与辉同行 **0%**），此时按用户去重的所有指标退化为 1，特征不可信。已加 `room.json` → `fansclub.uid_masked` 标记，使用前须检查。

**结构性限制（重要）**：能做粉丝团个体分析的房间（带货，未打码）恰好信息量低；信息量可能高的房间（娱乐团播，粉丝团活跃、`club_name` 有值）恰好打码，做不了按用户分析。→ **当前采集路径下粉丝团的价值主要在群体级，不在个体级。**

**待定标**：① `user_fans_club_status` 的 1 与 2（两房间分布不同，成因未定）。② `FansclubMessage.type=6` 语义曾定标为「灯牌点亮」但**已决定不采用**（完整性不可测 + 到达爆发），见 `modify.md` 2026-09-29（续）。
